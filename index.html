Group participation detection

Who is looking at whom, from one 360° camera.

A 360° camera sits among a group of people. This project works out, frame by frame, where each person is looking and which other person that is. That gaze data is a building block for measuring how a group participates.

This guide covers the two parts you will work on: src/c_impl, a C++ desktop app that runs the vision pipeline, and src/python_client, which listens to that app and scores it against hand-made labels. The demos run the same maths as the code, so you can change an input and watch what the code would do.

The whole system in five sentences

  1. The app reads a 360° video frame, and you pick who to track by clicking them once.
  2. For each person it cuts a normal-looking perspective crop out of the panorama, aimed at their head.
  3. Neural networks estimate head pose and eye gaze in that crop, which are combined into one 3D gaze ray.
  4. A Bayesian model turns those rays into a probability that each person is looking at each other person, or at no one.
  5. Results stream over gRPC to a Python client, which compares them with human labels and reports accuracy.
Orientation

Get it running

The project targets Windows with Visual Studio 2022. Four things you need are deliberately not in git (marked below), so a clone alone will not build or run. Ask the team where the current copies live.

Setup checklist

Your progress is saved in this browser.

Build the C++ app

From PowerShell, in the repo root:

cd src\c_impl
mkdir build -Force
cd build
cmake -G "Visual Studio 17 2022" -A x64 ..
cmake --build . --config Release --parallel

That produces src/c_impl/build/Release/tracker.exe. Protobuf code for C++ is generated during the build, so you never edit it by hand.

Set up the Python client

cd src
pip install -r python_client\requirements.txt
python python_client\build_scripts\proto_codegen.py

The generated Python files are committed, so codegen is only needed after rapport.proto changes.

Run an evaluation

Use two terminals. The client can start first: it waits for the tracker.

Terminal 1, from src

python python_client\rapport_cli.py serve --ground-truth ground_truth.csv

Terminal 2, from src\c_impl\build\Release

.\tracker.exe

You must start the tracker from build/Release. It finds models at ../../models relative to the working directory, not relative to the program (). It also overwrites gaze_analysis.csv in that folder at every launch.

  1. Click Open Video and choose the video. YOLO draws a red box around every person it finds.
  2. Click the people to track in the order P1, P2, P3. Boxes turn green and show the click order.
  3. Click Start Tracking. Check that the number on each green box matches your labels. If they differ, add an ID map to the client, for example --id-map 1:2,2:3,3:1.
  4. Leave the slider alone, because seeking replays or skips frames and skews the scores.
  5. When the client says it has passed the last label, press Ctrl+C in Terminal 1. It prints the report and saves it to logs/report_N.jsonl and logs/report_N_summary.json.

Unticking Show Video and Show 3D skips that drawing and makes long runs faster. To list the mistakes that lasted at least 2 seconds:

python python_client\rapport_cli.py replay --log-path logs\report_1.jsonl

System map

There are two processes. tracker.exe does all of the vision work and exposes a gRPC server. The Python client connects to it as a consumer. Everything in the C++ app runs on the Qt main thread, driven by a timer, except gRPC's own threads. Click any box to see what it owns.

Orientation

One frame, start to finish

Every 25 ms a Qt timer fires and one video frame goes through the whole pipeline. The processing is slower than the timer, so frames take as long as they take, but none are skipped. Step through what happens and what data exists after each stage.

When does YOLO run?

YOLO scans the whole panorama and is too slow to run on every frame. After the first click-based selection it only runs when something asks for it. This is the logic in :

Vision pipeline

Panorama to crop

A 360° frame is equirectangular: left to right is longitude, top to bottom is latitude. Straight lines bend, and faces near the edges stretch. The face networks expect an ordinary camera image, so PanoViewer simulates a virtual pinhole camera per person and renders a 640×480 view.

Each person's PanoViewer is aimed once, when YOLO supplies a box (). It stays fixed until the next YOLO update. Drag on the panorama, or pick a person, to see the footprint of the virtual camera and what it renders.

How a virtual camera is aimed

  • Yaw comes from the box centre: x / width × 360° − 180°.
  • Pitch starts at the top of the person box and moves down by 0.3 × FOV, so the head lands in the upper part of the crop.
  • FOV () assumes a head is 15% of the person's height, then chooses a zoom that makes the head roughly head_height_ratio of the crop height, clamped to 20°–110°. A tall box means a close person and a wider FOV.

The rendering uses precomputed lookup tables (map_x, map_y) and cv::remap. They rebuild only when yaw, pitch or FOV change, so the per-frame cost is one remap per person. See .

Vision pipeline

Head, eyes and gaze

Four networks run through ONNX Runtime on the CPU. Three run on each person's crop; YOLO runs on the whole panorama. detect() in connects them.

Step 1: L2CS turns bins into an angle

L2CS does not output an angle. It scores 90 bins, each 4° wide, covering −180° to +176°. The code applies a softmax and takes the expected bin (). Its "confidence" is the highest single-bin probability, averaged over yaw and pitch. A broad, unsure distribution gives a low confidence.

Step 2: head and eyes are blended

Head pose is stable but ignores the eyes. L2CS sees the eyes but gets noisy on low-quality faces. So the code keeps the head as a base and adds an eye correction scaled by confidence. Because L2CS already includes some head rotation, 40% of the head angle is subtracted first (kAlpha) to avoid counting it twice.

The comment in that code says 12% and 25%, but the constants are 20 and 40. The demo uses the constants, which is what runs.

Step 3: crop space to world space

This convention surprises most people: yaw 0, pitch 0 means looking straight back at the camera, not "straight ahead". The local frame is built with forward pointing from the person to the camera. Drag the person around the camera and try the yaw slider.

The world frame has its origin at the camera, +Y up, +Z at the panorama's centre column (yaw 0), and +X to its right. Positions are in centimetres. The pose estimator gives position in millimetres, and the code divides by 10 and truncates to an integer. Yaw and pitch are also truncated to whole degrees, so Pose carries ints:

Vision pipeline

Face ROI tracking

The localizer is skipped when it isn't needed. Once a face has been found, the pose estimator's own face box becomes the region of interest (ROI) for the next frame, smoothed with an exponential filter. The localizer reruns only if that ROI has drifted away from where the localizer last placed it (IoU below 0.25), or if tracking was lost.

ROI coordinates only mean something inside one person's crop, so the state must be per person. This has already gone wrong once: for a while a single ROI lived on OPNetTracker, and each person started from the previous person's face box. Step through both versions.

The state now lives on each Sort::Track (). Tracks are recreated when YOLO re-aims the cameras, so the ROI resets exactly when its coordinates stop being valid.

Vision pipeline

Keeping person IDs

Labels say "P1 looked at P2", so a person must keep the same ID for the whole video. That is the job of Sort (), a variant of the SORT tracker. It runs in two layers:

  1. Internal trackers. Each has a Kalman filter that predicts where the head box will be. Predictions are matched to detections with the Hungarian algorithm on IoU. A pair below iou_threshold (0.15) does not match, and an unmatched detection creates a new tracker with a new internal ID.
  2. Display IDs. Because num_people is known, any internal ID above it is remapped to a free display ID from 1 to num_people (). A person who is lost and re-detected gets their old display ID back, as long as it is the only free one.

Click order only works if every pose succeeds on the first frame. IDs are handed out in the order gazes arrive. If the second person you clicked has no pose on that frame, the third person takes ID 2. That is why step 3 of the run instructions asks you to check the numbers on the green boxes.

If two people are lost in the same frame, the display IDs can swap. The code has a comment admitting this. Trackers survive 1000 frames unmatched (max_age), and missed frames decay their velocity by velocity_decay so a lost box does not drift away ().

Vision pipeline

Who is looking at whom

This is the saliency-aware step (). For each observer, independently, it computes a probability over who they are looking at: every other person, plus a null target that means "no one in particular". The null target is what lets the model say someone is looking at the robot or the table.

Bayes' rule: posterior(target) ∝ likelihood(target) × prior(target)

  • Likelihood: does the gaze ray point there? A Gaussian on the horizontal and vertical angle between the ray and the target's head. The two widths differ: sigma_x is wide because horizontal gaze estimates are looser, and sigma_y is narrow. Anything behind the observer scores about zero. The null target has a constant likelihood.
  • Prior: is this target worth looking at? People look at whoever is moving, which is the "saliency" part. Each target's score is omega_base + omega_motion × motion, and the null target's is omega_null. A softmax turns the scores into probabilities.

Drag people around, drag the arrow to aim the observer, and change the settings. Every number is computed by a verified port of the C++.

What to know when tuning

  • is_looking is just the most likely target. There is no threshold, so is_looking is true for a target with a posterior of 0.34 if nothing beats it.
  • Defaults are not what runs. tracker_settings.ini overrides the defaults in . Load both presets in the demo to compare them.
  • Motion is a one-frame measure: how far the head box moved in its crop since the last frame, divided by the box diagonal and clamped to 0–1 ().
  • With only one person detected there are no edges at all (). The evaluator counts those frames as no_prediction.
Output and testing

The gRPC stream

The contract between the two processes is one file: src/c_impl/proto/rapport.proto. The app is the gRPC server, on 127.0.0.1:50051 by default, and the client calls a single server-streaming method. You can change the address with the RAPPORT_GRPC_TARGET environment variable.

Each frame with at least two detected people gives one edge per ordered pair: three people means six edges. probability values for one observer add up to at most 1, and the remainder is the probability of looking at no one.

The queue drops old frames on purpose

The tracker must never block on a slow client. So publish() pushes into a bounded queue (256 by default, set with RAPPORT_GRPC_MAX_QUEUED), and when it is full the oldest frame is thrown away.

That has a consequence for testing: dropped frames are never scored. The evaluator detects jumps in frame_index and warns you. Try to make it happen:

  • One queue, one reader. Two clients compete for frames, so each sees a partial stream. Run one client at a time.
  • The stream has no end marker. At the end of the video the tracker simply stops publishing. You end the run with Ctrl+C or by closing the app.
Output and testing

Scoring against labels

Labels come as time intervals in a CSV: start_time, end_time, duration, label_type, where label_type looks like P1GazeP2 or P1GazeRobot. Times are in seconds of video, and are matched to each frame's playback_timestamp_ns.

At each frame, each labelled person has a set of accepted targets (). The rules matter, because they decide what the score means:

SituationHow it is scoredWhy
P1GazeRobotAccepted target is no_personThe model has no robot class, so "no one" is the right answer
No label active for a personThat person is skipped for that frameThe annotators made no claim, so it cannot count as right or wrong
Two labels overlapEither target counts as correctAnnotators disagree or the person changed target mid-interval
After the last labelNothing is scoredThe pilot labels end at 305 s, and the video runs to 646 s

Reading a report

The client prints this at the end of a run and saves it as report_N_summary.json. Read it in this order:

  1. Warnings. Jumps in frame_index mean frames were dropped or the video was seeked, so the scores may be off. If every probability is 0, your tracker.exe is out of date.
  2. Accuracy against the baseline. The report also prints what always answering "no one" would score. Compare with that, not with 0, because no one is a common answer.
  3. Per-person accuracy. One person far below the others often points to a tracking or crop problem, not the gaze model. Check no_prediction too.
  4. The confusion matrix. A strong diagonal means the IDs line up. A busy no_person row means looks at the robot are being given to people, which is what omega_null and likelihood_null_baseline control.
  5. Edge metrics. AUROC, average precision and Brier score judge the probabilities themselves. The threshold table shows what a cut-off other than the most likely target would do.

How do I…

The usual edits touch several files that must stay in step.

Add a field to the stream
  1. Add it to rapport.proto with a new field number. Never reuse or renumber one, and note that numbers 100–199 on PipelineUpdate are reserved.
  2. Add it to the matching struct in domain/types.h.
  3. Fill it in where the data is made, for example GazeBayesMapper::infer.
  4. Copy it onto the message in mapToPipelineUpdate. This is the step people forget: it compiles without it and sends 0.
  5. Run python python_client\build_scripts\proto_codegen.py, commit the regenerated stubs, and rebuild tracker.exe.
  6. Read it in GazeEvaluator.handle_update.
Add a tunable setting
  1. Add it to TrackerConfig with a default, or to GazeBayesConfig for the gaze model.
  2. Save it in saveDefaults and load it in loadDefaultsInto.
  3. Add a widget in showSettings, and read it in collectConfig. Without that second step the dialog shows the value but changing it does nothing.
  4. Pipeline code reads it through tracker_.getConfig(). Settings that go to another object, like the IoU threshold, must also be forwarded in VisionPipeline::setConfig.
Tune the gaze model
  1. Open the Settings dialog in the app and change the gaze values. Click Set as Default to write them to tracker_settings.ini.
  2. Keep every other setting and the click order the same, and run the full labelled section.
  3. Compare two report_N_summary.json files: overall accuracy, then per-person accuracy, then the confusion matrix. Use AUROC to tell whether the probabilities themselves improved.

The settings live in one ini file per build folder, so note them with your results. A Debug and a Release build do not share them.

Swap or add a model
  1. Load it in OPNetTracker::initialize, following the other models.
  2. Write a small wrapper class in model_core.cpp. Check its expected input size, channel order and normalisation: each existing model differs.
  3. Call it from detect(). That runs per person, so per-frame cost multiplies by num_people.
Track a different number of people

Change Num People in Settings. Sort, re-selection and display IDs all follow num_people. Set it before opening a video, because selection asks for exactly that many clicks. Labels must use IDs that match, or pass --id-map.

Add an evaluation metric
  1. Collect what you need per frame in GazeEvaluator.handle_update.
  2. Compute it in summary() or _edge_metrics, which puts it into the JSON file.
  3. Add a line in format_summary to print it.
Debug when the client shows nothing
  1. The client prints Waiting for tracker updates and stays quiet until you click Start Tracking. It prints progress every 300 frames.
  2. If every probability is 0, your tracker.exe predates the proto change: rebuild it. The report warns about this.
  3. If the app seems healthy but the client gets nothing, check that port 50051 is free. If it is taken, the app shows a "gRPC stream unavailable" warning at startup.
  4. If accuracy is near chance on every person, suspect the ID mapping before the model. A confusion matrix without a strong diagonal is the sign.
  5. If accuracy is poor and the IDs are right, check that the labels and video share a time base. Timestamps come straight from the video file ().

Sharp edges

Things that have caught people out, or that look like open issues. Trap means it will surprise you. Likely bug means behaviour that looks unintended. Debt means something worth cleaning up.

Glossary

TermMeaning here
EquirectangularThe 2:1 panorama format. Pixel x is longitude and pixel y is latitude.
Perspective view / cropThe 640×480 image rendered by a PanoViewer for one person.
ROIRegion of interest: the box around a face inside a crop.
Gaze rayA head position plus a unit direction, in world coordinates. PanoViewer::gaze holds one per person.
Observer / targetThe person whose gaze is being explained, and a candidate for what they are looking at.
Null targetThe "no one" outcome of the gaze model. Scored against Robot labels.
Prior, likelihood, posteriorBefore seeing the gaze ray, how much the ray supports a target, and the final combined probability.
SaliencyHere, the idea that moving people attract gaze. It enters through omega_motion.
EdgeOne ordered pair (from, to) in a frame, with an angle, a flag and a probability.
IoUIntersection over union: overlap between two boxes, from 0 to 1.
Selection modeThe paused state where you click people to track. Also triggered when tracking is lost.
Display IDThe stable 1 to num_people ID shown on boxes and sent in the stream.
AUROCThe chance a true edge gets a higher probability than a false one. 0.5 is random and 1 is perfect.
Brier scoreMean squared error of the probabilities. Lower is better.
